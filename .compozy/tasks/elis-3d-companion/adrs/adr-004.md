# ADR-004: On-Demand Render Loop with Device Tiers and Rest Pausing

## Status

Accepted

## Date

2026-06-13

## Context

Elis is a secondary delight on a reading-first site; she must not regress page
load or scroll smoothness and must degrade gracefully on weak/mobile GPUs (PRD
High-Level Technical Constraints and Success Metrics). The prototype runs a
default continuous `frameloop` with no DPR cap, no device tiering, and no
`prefers-reduced-motion` handling — it renders every frame even when the cat is
idle and even when the tab is hidden.

On a reading-first site Elis is at rest (sleeping, minimal pose, quiet mode) the
majority of the time, so continuous rendering wastes battery and CPU for no
visible benefit.

## Decision

Bound the runtime cost with three combined mechanisms:

1. **On-demand render loop** — the Canvas runs `frameloop="demand"`. While Elis
   is _active_ (walking, stretching, playing, glancing in motion) the loop
   self-drives via `invalidate()` each frame. When she enters a _rest_ state
   (sleep/minimal pose), when quiet mode engages, when the tab is hidden
   (`visibilitychange`), or when the overlay leaves the viewport
   (IntersectionObserver), the loop stops and the last frame stays on screen.
2. **DPR cap** — `dpr` is capped (≈ [1, 2], lower on low tiers) so retina
   devices do not pay full pixel cost for a small corner overlay.
3. **Device tiers** — a lightweight heuristic (viewport width / coarse-pointer
   / `prefers-reduced-motion`) classifies the device into a small set of tiers
   that scale animation richness and gate features. Tier 0 (weak GPU /
   `prefers-reduced-motion`) is ambient-only and near-static. Tier 1 (capable
   mobile) gets the full experience including touch-drag play. Tier 2 (desktop)
   gets the full experience. Play mode is disabled only on tier 0.

## Alternatives Considered

### Alternative 1: Continuous loop, pause only when hidden

- **Description**: Default `frameloop="always"`, pausing only on
  `visibilitychange` / off-viewport.
- **Pros**: Simplest; animation always ready.
- **Cons**: Renders every frame even while Elis is idle and on-screen — the
  common case on a reading page — wasting battery on mobile.
- **Why rejected**: Misses the largest saving (idle-on-screen) and gives weaker
  budget control.

### Alternative 2: Single conservative profile, no tiers

- **Description**: One lean profile for everyone (low DPR, few clips), no device
  detection.
- **Pros**: Less code to maintain.
- **Cons**: Wastes desktop headroom while still potentially heavy on the weakest
  phones; no `prefers-reduced-motion` path.
- **Why rejected**: Fails graceful-degradation and accessibility goals at both
  ends of the device spectrum.

## Consequences

### Positive

- Render cost tracks actual motion, not wall-clock time.
- Explicit ceiling (DPR + tier) bounds the worst case.
- `prefers-reduced-motion` and mobile degradation are first-class.

### Negative

- More orchestration code: the store must expose an accurate "active vs rest"
  signal and the Canvas must wire visibility/viewport observers.
- Tiers add branching in the behavior and asset-quality selection.

### Risks

- **Stale frame after resize/theme change** — mitigated by invalidating once on
  such events so the static frame repaints.
- **Mis-tiering a capable device** — mitigated by keeping tier rules simple and
  erring toward the conservative tier when uncertain.

## Implementation Notes

The "active vs rest" signal comes from the ADR-003 store. Quiet-mode detection
(sustained scroll + article dwell) reuses `use-scroll-position` and the
IntersectionObserver pattern from `use-anchor-observer`.
