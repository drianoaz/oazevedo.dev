# ADR-003: Mood/Energy State in an External Store Driven by the Render Loop

## Status

Accepted

## Date

2026-06-13

## Context

ADR-001 commits Elis to a living-pet simulation: an internal mood/energy model
that evolves over time and drives semi-autonomous behavior. That state must
tick continuously (decay, timers, transitions) and feed the render loop every
frame, while a small slice of it (current mood label, dismissed/silenced
preference) also drives plain React UI such as the dismiss control.

The project today has **no state library** — the only React Context is the
table-of-contents provider. Updating React state at frame rate causes a
re-render per frame and risks jank on a reading-first site where smoothness is
a must-hold metric.

## Decision

Keep the mood/energy state in a **plain external store** (a module-level object
plus a reducer/`tick(dt)` function), updated **inside the R3F `useFrame` loop**.
The store exposes:

- An imperative API for the simulation and behaviors to read/mutate per frame
  (no React involved on the hot path).
- A `subscribe`/`getSnapshot` pair consumed by React via `useSyncExternalStore`
  **only at the UI boundary** (dismiss/silence control, debug surfaces), so the
  DOM re-renders just when a discrete, user-visible value changes.

No new dependency is added; the store is a single file under
`src/components/elis/`.

## Alternatives Considered

### Alternative 1: zustand

- **Description**: Adopt zustand as the global mood/energy store.
- **Pros**: Ergonomic selectors, easy testing, transient updates supported.
- **Cons**: New runtime dependency in a project that has zero state libs;
  more than the feature strictly needs.
- **Why rejected**: YAGNI — `useSyncExternalStore` + a hand-rolled store covers
  the need without a dependency.

### Alternative 2: React Context + useReducer

- **Description**: Reuse the table-of-contents Context pattern for mood state.
- **Pros**: Familiar to the codebase; no new concepts.
- **Cons**: Re-render on every mood change and awkward for per-frame ticks;
  pushes simulation timing into React's render cycle.
- **Why rejected**: Frame-rate updates through Context risk jank, violating the
  reading-smoothness guardrail.

## Consequences

### Positive

- Zero React re-renders on the per-frame simulation path.
- Clear seam between simulation (imperative, hot) and UI (declarative, cold).
- No new dependencies.

### Negative

- Manual tick/decay/timer bookkeeping instead of a library's conveniences.
- The team must be disciplined about not reading store internals from React
  outside the `useSyncExternalStore` boundary.

### Risks

- **State/animation desync** — mitigated by making the store the single source
  of truth that both the animation selector and the UI read from.

## Implementation Notes

The store lives at `src/components/elis/elis-store.ts`. The render strategy in
ADR-004 uses the store's "at rest vs active" status to decide when to pause the
loop.
