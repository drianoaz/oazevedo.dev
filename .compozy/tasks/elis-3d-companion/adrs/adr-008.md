# ADR-008: Validation Strategy — Vitest for Simulation Logic, Playwright for Guardrails

## Status

Accepted

## Date

2026-06-13

## Context

The repository today has **no test framework** (CLAUDE.md: "There is no test
framework — use `lint`, `check:types`, and `check:prettier` to validate code
quality"). Elis introduces two qualitatively different risks that those static
checks cannot cover:

1. **Simulation correctness** — the mood/energy store (decay, interaction
   boosts, energy→mood thresholds, RNG jitter), the clip transition table, and
   the quiet-mode detector are pure-ish logic where a silent regression would
   make Elis behave wrong without any type or lint error.
2. **Reading guardrails (P0)** — the must-hold promises: Elis never steals focus
   or scroll, never overlaps the article body, quiet mode engages during active
   reading, `prefers-reduced-motion` renders her static, and the
   dismiss/silence preference persists across reload and navigation. These are
   behavioral, cross-cutting, and browser-dependent.

ADR-003 already shaped the simulation to be testable (pure functions, external
store) and ADR-007/the TechSpec specify a seedable RNG and simulated time.

## Decision

Adopt a **two-layer automated validation strategy**, accepting two new dev
dependencies (and updating CLAUDE.md to reflect the new reality):

1. **Vitest — simulation unit tests.** Unit-test the pure logic in
   `src/components/elis/` (store `tick`/decay/thresholds, `behaviors.ts`, clip
   transition selection, quiet-mode detection) using **seeded RNG** and
   **injected/simulated time**, so runs are deterministic. Scope is deliberately
   narrow: only the framework-free, side-effect-free logic.
2. **Playwright — guardrail E2E.** Drive a real browser to assert the P0
   guardrails: focus is never trapped/stolen, page scroll is never hijacked,
   the article body is never overlapped, quiet mode engages on sustained
   reading, `prefers-reduced-motion` yields a static Elis, and
   dismiss/silence persists across reload **and** route navigation.

**Explicit limitation:** neither layer reliably asserts 3D **scroll-smoothness /
FPS** — the must-hold performance budget. That stays a **manual, assisted check**
(DevTools Performance panel: scroll FPS with Elis present vs removed, on desktop
and a real mid-range phone), backed by a reproducible checklist and the dev
debug overlay (mood/energy/tier/quiet/fps).

## Alternatives Considered

### Alternative 1: Stay framework-free (debug harness + manual checklist)

- **Description**: No runner; validate via the dev debug overlay and a manual
  checklist only.
- **Pros**: Zero new dependencies; fully faithful to the current CLAUDE.md.
- **Cons**: The riskiest part (emergent simulation) has no deterministic safety
  net; guardrails rely entirely on human discipline → silent regression risk.
- **Why rejected**: The simulation and P0 guardrails are too important to leave
  unautomated for a reading-first site.

### Alternative 2: Vitest only (no E2E)

- **Description**: Unit-test the logic; verify guardrails manually.
- **Pros**: Covers the highest-risk logic with one dependency.
- **Cons**: The P0 guardrails (focus/scroll/persistence/reduced-motion) are
  exactly the promises most worth automating and are browser-behavioral.
- **Why rejected**: Leaves the must-hold reading guarantees unprotected against
  regression.

### Alternative 3: Lighthouse CI

- **Description**: Add Lighthouse to CI for perf/a11y metrics per PR.
- **Pros**: Automated metric regression detection.
- **Cons**: Does not cover Elis-specific behaviors (quiet mode, focus, scroll
  hijack); more CI infrastructure.
- **Why rejected (as primary)**: Wrong tool for behavioral guardrails; may be
  added later as a complementary metric gate, not the core strategy.

## Consequences

### Positive

- Deterministic safety net on the emergent simulation (seeded RNG + sim time).
- The must-hold reading guardrails are automated and regression-protected.
- Test scope stays tight: only logic and guardrails, not exhaustive UI.

### Negative

- Two new dev dependencies (Vitest, Playwright) and the CI/time to run them;
  CLAUDE.md must be updated from "no test framework".
- E2E adds setup and maintenance for a secondary delight.
- The performance must-hold remains manual — not fully automated.

### Risks

- **E2E flakiness around 3D/timing** — mitigated by asserting DOM/behavioral
  facts (focus, scroll position, attributes, localStorage), not pixels or FPS.
- **Scope creep into broad UI testing** — mitigated by limiting Vitest to pure
  logic and Playwright to the documented guardrail checklist.
- **Perf regression slipping through** — mitigated by the mandatory manual
  DevTools profiling step in the release checklist.

## Implementation Notes

- Vitest config and `*.test.ts` colocated with the logic under
  `src/components/elis/`; add `npm run test` and keep `lint`/`check:types`/
  `check:prettier` as-is.
- Playwright specs under a top-level `e2e/`; guardrail checklist mirrors the
  TechSpec Testing Approach.
- Update `package.json` (devDeps + scripts) and CLAUDE.md's "no test framework"
  note. The seedable RNG and injected clock come from the ADR-003 store design.
